## 2026-09-11 - Plush RNG Engine Weight Calculation Allocations
**Learning:** In the Plush RNG engine, calculating rarity weights (`_buildWeightTable` and `pity.getMultiplier`) evaluates every rarity on every roll (~300 items). Re-deriving pity configuration objects (`resolveConfig`) and computing BigInt denominator values (`denomBig`) on every query generated over 600 allocations per roll, limiting roll throughput to ~516 rolls/sec. Memoizing static pity configs and BigInt denominators in `WeakMap` caches nearly doubled throughput to ~971 rolls/sec (~48% latency reduction per roll).
**Action:** Always cache/memoize static configuration objects and BigInt conversions when iterating over large datasets inside hot loops like RNG roll calculators.

## 2026-09-11 - Plush RNG Engine Pity Multiplier Threshold Fast-Path
**Learning:** In the Plush RNG engine, `pity.getMultiplier` is evaluated for every item (~555 rarities) during roll weight generation. Because `PityTracker.prototype.increment` increments counters for all eligible items on each roll, `count` quickly becomes non-zero for hundreds of items. A naive `if (!count)` check fails because `count > 0`, forcing `getMultiplier` to execute mastery Map lookups and `Math.round`/`Math.max` threshold arithmetic for ~500 items per roll even when `count` is far below early pity start. Precalculating `minEarlyPity = Math.max(1, Math.floor(earlyPityStart * (1 - MASTERY_CAP)))` on static pity configs allows `if (count < config.minEarlyPity) return 1.0;` to safely bypass mastery lookups and threshold math for all sub-threshold pity counts, cutting `pity.getMultiplier` latency by ~91.8% and increasing roll throughput from ~829 to ~1007 rolls/sec (+21.5%).
**Action:** Precalculate mathematical lower bounds on complex multi-variable threshold formulas in hot loops to allow simple integer comparisons to short-circuit calculation early.

## 2026-09-12 - Plush RNG Engine Weight Calculation Division Simplification and Mult Fast-Path
**Learning:** In `PlushRoller._buildWeightTable`, calculating `(SCALE * multBig) / (denom * MULT_PRECISION)` for ~555 rarities per roll multiplies two 128-bit BigInts by 10^9 and 10^6 and divides large BigInts. Since 10^9 / 10^6 = 1000, pre-declaring `SCALE_REDUCED = SCALE / MULT_PRECISION` (1000n) at module scope simplifies the calculation to `(SCALE_REDUCED * multBig) / denom`. Additionally, adding `if (mult === 1.0) w = SCALE / denom;` bypasses `Math.round` and `BigInt` conversion entirely when no multipliers are active. This improved roll throughput by ~12.5% (from ~1030 to ~1159 rolls/sec). Note: Declaring `1000n` as an inline literal inside the hot loop caused a -15% slowdown due to repeated BigInt allocations; declaring it as a module constant was critical.
**Action:** Simplify large constant arithmetic fractions before executing BigInt division in hot loops, and ensure BigInt literal constants are declared at module scope rather than inside hot loops to avoid per-iteration allocations.

## 2026-09-12 - Plush RNG Engine O(1) Step-Based Pity Tracking
**Learning:** Mutating ~550 Map entries per roll (`pity.increment(r.name)`) generated over 27.5 million Map lookups/mutations per 50,000 rolls in `PlushRoller.roll`. Refactoring `PityTracker` to maintain a global integer step offset (`pity.advance()`) and recording reset steps per rarity (`_lastResetStep`) converts pity calculations to $O(1)$ relative offsets `_step - lastResetStep`. This increased roll throughput from ~4,773 rolls/sec to ~6,195 rolls/sec (+29.8% speedup).
**Action:** Replace $O(N)$ per-item increment loops on large collections with global step/timestamp offset tracking to achieve $O(1)$ per-iteration performance in hot simulation loops.

## 2026-09-12 - Plush RNG Engine Base Multiplier Hoisting and Empty-Map Fast Paths
**Learning:** In `PlushRoller._buildWeightTable`, calculating per-item multipliers evaluated redundant global terms (`streakMult * momentumMult * (luckBoostActive ? 4 : 1) * luckMultiplier * fortuneMult`) and queried `this.resistance` and `this.streak` Maps for all ~555 rarities on every roll. Hoisting constant base multipliers outside the loop eliminated 2,000+ per-roll floating-point multiplications. Additionally, adding `if (this._map.size === 0) return 1.0;` fast-paths to `ResistanceTracker` and `StreakTracker` bypassed ~1,100 unnecessary Map lookups per roll when no cooldowns or dry runs were active. Caching `noticeable` and `minW` metadata per rarity in a `WeakMap` reduced roll latency by 53.9% (increasing throughput from ~1,315 to ~2,850 rolls/sec).
**Action:** Always hoist invariant terms outside of large item iteration loops, and check collection `.size === 0` before querying items in hot paths.

## 2026-09-17 - Inventory List Item Update Fast-Path and Event Handler Deduplication
**Learning:** In `main.js`, `updateItem` was called on every roll landing on an existing inventory item. It previously aborted the element's active `RarityStyle` animation controller, reset element inline styles, and restarted the animation context from step 0. It also allocated a new double-click event listener closure and rebound it to the DOM node on every roll. Fast-pathing `updateItem` to check `if (!liElement._rarityStyleAC || liElement._rarityStyleAC.signal.aborted)` before applying styles, attaching the sell handler once (`if (!liElement._sellHandler)`), and reusing `_newRollTimer` reduced 5,000 `updateItem` calls from 159.1ms to 24.7ms (~84.5% latency reduction), eliminating visual animation stutter and per-roll object allocations.
**Action:** When updating existing DOM list items on high-frequency events, preserve active animation loops and event listeners instead of destroying and re-instantiating them on every item count increment.

## 2026-09-17 - Gauntlet Rarity Map Lookup and Rotation Memoization

**Action:** Replace linear array searches over static configuration lists with Map lookups in periodic DOM rendering functions, and memoize deterministic rotation/seed calculations.
